# Working on this repo

Rockbox fork for the HiBy R1, on top of bahusoid's Audiobook Mod. C89-ish C, a
huge upstream tree, and a small set of files that are actually ours. Read
`README.md` for what the fork adds and `docs/index.md` for the per-feature docs.

## Where our code lives

Almost every change is in one of these:

| Area | Files |
| --- | --- |
| Stick / touch input | `apps/stick*.c`, `tools/stick_test/` |
| Compositor, layers | `apps/canvas.c`, `firmware/drivers/lcd-layers.c` |
| Skin engine | `apps/gui/skin_engine/`, `apps/gui/wps*.c` |
| Library views | `apps/gui/`, `apps/tagtree.c` |
| Audiobooks | `apps/audiobooks/` |
| Themes | `themes/`, generated by `themes/gen_skins.py` |
| Device | `firmware/target/hosted/hiby/` |
| Build/release | `.github/workflows/`, `tools/release/` |

Everything else is upstream Rockbox. Do not reformat, "clean up" or refactor
upstream files. Touch them only where the feature needs it, in the style of the
surrounding code.

## Rules

* **Match the neighbours.** Comment density, naming, brace style and error
  handling come from the file you are editing, not from your own preferences.
* **Smallest change that works.** No new abstraction, config option, helper
  layer or dependency unless the feature cannot land without it. When a stdlib
  or existing Rockbox helper does the job, use it. See the `ponytail` skill.
* **No speculative work.** No "while I was in here" edits, no unrequested
  refactors, no new settings nobody asked for.
* **Never touch the boot path or physical keymap** unless the task is about
  them - CI fails the build if a stick change diffs the input floor
  (`.github/workflows/build.yml`).
* **Settings** need the whole chain: `settings_list.c`, `settings.h`, lang
  strings in `apps/lang/english.lang`, and a config.cfg round trip.
* **Memory.** The R1 is a hosted target but still small: no per-frame malloc,
  no unbounded buffers, free what you allocate.

## Build and test

```sh
make -C tools/stick_test test          # stick engine, seconds, no toolchain
mkdir -p build && cd build && ../tools/configure   # full build needs the toolchain
```

The stick tests are the fast gate - run them for any input change. A full
device build is CI's job (`.github/workflows/build.yml`); do not burn tokens
waiting on one locally unless the task is about the build itself.

## Issues and PRs

Every issue you pick up gets a PR, and every PR points back at its issue:

* **One issue, one PR.** Open it against `master` with `Closes #<n>` in the body
  so merging closes the issue.
* **Label the issue** from `.github/labels.yml` before you start: one `type:`,
  one `area:`, one `severity:`, plus `needs:`/`blocked`/`upstream` where they
  apply, and drop `needs: triage` once it is sorted. Keep them current as the
  work moves - status that no label covers goes in a comment.
* **Comment the outcome on the issue** when the PR is up: what was done, the PR
  link, anything still open.

## Proof

A claim is not evidence. Anything user-visible ships with a screenshot in the PR
description, and in the issue comment when it answers the report:

* Capture frames by driving the simulator headlessly - `~/rb/wtNNsim.sh` to
  build, then `~/rb/wtNNsimctl.sh script.txt outdir`. Commit shots under
  `docs/mods/screenshots/` only when they belong in the docs; otherwise attach
  them to the PR.
* Before/after pairs for anything that changes existing behaviour.
* Non-visual work proves itself with pasted command output: the stick test run,
  the config.cfg round trip, the failing-then-passing repro.

## CI

A PR is not done until **every** check is green. Push, watch the run, fix what
it reports, push again - never hand over a PR with a red or pending check, and
never ask for a merge around one. If a failure is genuinely unrelated to the
change, say so on the PR and quote the log line that shows it.

## Commits and PRs

Conventional Commits, enforced on the **PR title** by
`.github/workflows/pr-title.yml` - the merge commit's body becomes the release
version bump.

```
feat(stick): kinetic coasting after a flick
fix(wps): large JPEG covers no longer fail to load
```

Types: `build chore ci docs feat fix perf refactor revert style test theme`.
Subject under ~50 chars, imperative, no trailing period. A body only when the
*why* is not obvious from the diff. Breaking change: `feat!:`.

PR description: what changed, why, how it was tested, the screenshot, and
`Closes #<n>`.

## Being cost-effective

These are the rules that keep an agent session cheap without making it worse:

* **Grep before reading.** This tree is enormous. `Grep`/`Glob` to find the
  handful of relevant files; never read a large upstream file end to end when a
  targeted range will do.
* **Answer from what you already have.** Do not re-read a file you just edited
  to "verify" it, and do not re-derive facts already established in the session.
* **One sweep, not a crawl.** Batch independent searches and reads in a single
  step instead of one round trip each.
* **Delegate fan-out, not focus.** A broad search across many directories is
  worth a subagent; a two-file edit is not - a subagent starts cold and re-reads
  everything you already know.
* **Effort to match the task.** A typo fix does not need a plan, a full test run
  or a design discussion.
* **Say less.** Terse output, no restating the diff in prose, no summary tables
  of what you just did. Code and commit messages stay written normally.
* **Keep caveman and ponytail on.** `caveman` keeps the prose terse, `ponytail`
  keeps the diff to the laziest thing that works; both belong in every session
  here. If either skill is not installed, ask the user to install it instead of
  working without it.
